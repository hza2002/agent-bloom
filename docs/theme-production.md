# 主题制作流程

## 当前接入状态

12 套主题均已接入本地生产 CLI；Windows 已并入 Microsoft。下方的「未接入」字样属于设计阶段历史记录，以本节为准。
新增 10 套共用文字动画、布局和安全调度，大图为离线帧资源。
本轮 12 套主题已完成用户逐套视觉验收，包括 Claude 小图、Codex 字形、标语与待机效果。
自动验证覆盖渲染、布局、PTY 生命周期、安装包与网站构建；发布前重新运行，
不把历史测试数量当作当前版本的证据。已发布版本以 CHANGELOG 和 GitHub Releases 为准。


本流程用于项目内部维护的主题。生产接口见 [themes.md](themes.md)。
先做可比较的网页原型，再接入终端；原型通过不等于已经进入 CLI 或可以发布。
不增加外部插件发现、通用动画配置语言或安装时素材转换依赖。

## 1. 先定义主题身份

每套主题提交一份设计单，写明：

| 项目 | 必须回答的问题 |
| --- | --- |
| 名称与 ID | 用户看到什么名称？稳定的小写 ID 是什么？ |
| 品牌年代 | 现代还是经典版本？不要混用不同时代的轮廓和字标 |
| 大图 | 静态终点是什么？不看文案能否认出主体？ |
| Claude 小图 | 哪个元素在 8/9/9 字符空间里最好认？可以与大图不同 |
| Codex 小图 | 现有单字符槽使用哪个可用字形？缺失时如何回退？ |
| 色彩 | 主色、辅助色、深浅背景各怎么保持可读？ |
| 文案 | 品牌相关主句、次句、平台行各是什么？哪些是原句，哪些是编辑文案？ |
| 动作 | 保留的开场讲什么动作？待机有什么明显但短暂的变化？ |
| 差异 | 与最接近的已有主题相比，至少一个轮廓差异和一个动作差异是什么？ |
| 来源 | 原始资源、版本、下载地址、适用署名要求和改编说明存在哪里？ |

优先保存官方矢量或高分辨率资源。使用第三方收录的轮廓要标明来源，
不能称为官方直接提供；自行绘制的像素图也不能称为官方 sprite。
品牌标志、字体、宣传语分别记录来源。项目代码许可证不代表品牌资产授权。
历史品牌资源明确注明年代；没有可靠素材时暂停该图形的定稿，不凭记忆仿写字标。

## 2. 静态画面先过关

先完成大图、字标、三行文案和小图，再做运动。共享排版沿用 Huawei / Apple：
主句加粗、次句适度字距、平台行用强调色与短横线；避免与 Claude、Codex 绑定的宣传文案。
文案不为了填满三行重复同一个意思，默认不加句末句号。

- 大图使用完整的几何边界，保留叶片、咬口、天线、眼形等识别特征；不能通过收紧边界裁掉轮廓。
- 用实色色块、半高和更细的块字形表达层次，不给边缘加背景混色或抗锯齿光晕。
- 小图独立绘制，不能只把大图缩小。以光学重心居中，不强行铺满宽度导致比例失衡。
- Claude 小图工作网格为 18×12，第一行字符占用少一格，对应左上 2×4 像素留空。
- 每个字符最多前景和背景两色；透明边界只留一个前景色。四分块模式单独检查，必要时提供专用小图。
- 大图与小图可以不同，但应有明确品牌关系，例如 Mario 人物搭配蘑菇。
- 小图选项是设计比较能力，不自动意味着新增 CLI 参数；生产默认值先确定一套。

## 3. 动画使用相同终点，动作必须不同

每个首版主题先做好一种开场和一种待机。第二种开场只有在质量独立过关、
动作确实不同且值得保留时才加入；数量不作为交付指标。

1. 开场 A 展示品牌的结构，例如拼合窗格、绕出椭圆、眼形扫描。
2. 额外开场必须使用另一种有意义的运动逻辑；较弱的方案直接移除。
3. 所有开场回到同一张静态大图、字标和文案，小图不会随随机开场变化。
4. 待机应在正常尺寸下看得见，最终精确回到静态画面；不留下亮边、残影或位移。
5. 不在每一帧随机取样。启动时确定动画候选，resize、clear、恢复后仍保留选择。
6. 不用大面积闪烁或持续运动吸引注意；尊重减少动态效果、提交、可见性及 `--no-ambient`。

网页当前开场固定 3 秒、待机 1.6 秒，是用于比较的节奏稿。
生产端采用 scene 的 duration 与现有调度器，当前待机间隔 8 秒、扫光 2 秒。
两者不能直接宣称帧级等价，接入后必须重新验收真实终端节奏。

## 4. 原型交付与自动检查

每个原型由 `prototypes/theme-lab/themes/<id>.js` 导出独立模块。
接口沿用现有模块：身份与文案、`variants`、可选 `badges`、`sources`、`note`、
`render(ctx, state)` 和 `mini(ctx, state)`。不新增框架。

大图 Canvas 为 192×128，小图为 18×12；`state` 包含 `phase`、`t`、`variant`、
`badge`、`light`。开场 `t` 为秒，待机 `t` 为 0 到 1，静态不依赖时间。
渲染函数不能自行安排计时、请求网络、读取输入或改变 DOM。
在 `catalogue.js` 显式登记，原始资源与来源说明保存在主题同名目录。

```sh
python3 -m http.server 8768 --bind 127.0.0.1 --directory prototypes
```

打开 `http://127.0.0.1:8768/theme-lab/` 比较原型，打开
`http://127.0.0.1:8768/theme-lab/checks.html` 运行共同检查。
检查页和预览共用 `pixels.js`，不维护第二套字符量化逻辑。

自动检查覆盖全部原型的深浅背景、八分块/四分块、所有开场与小图组合：

- 静态图、小图非空；ID 唯一，有三行文案与来源入口。
- 每种开场在 2.9、2.99、2.9999 和 3 秒处均与静态图逐像素相同，避免结束时强行补图。
- 全程每 0.05 秒检查时间点两侧的大幅跳变，允许一个子像素的栅格步进；这是粗筛，细小闪变和美感仍需实际播放验收。
- 待机首尾与静态逐像素相同，中间采样存在变化。
- 切换小图不改变静态大图，切换开场不改变小图。
- 不同小图选项经过字符降级后仍有区别。

自动检查只能发现合约错误，不能证明图形像品牌、动作好看或来源许可完整。
检查截图还要覆盖开场中段、静态、待机中段、明暗背景、两种字符精度、标准/紧凑空间和窄屏。
遮挡、过宽、字形失真、低对比或难以察觉的动作均需修正后再选定。

## 5. 接入生产与发布验收

依照 [themes.md 的 Add a theme](themes.md#add-a-theme) 接入 Python 主题注册表。
复用现有 Scene、布局、字形编码和 PTY 安全边界。不要为品牌在共享传输代码里加分支。
渲染器保持延迟导入；安装和运行不依赖浏览器、Node、在线素材或绘图工具。

生产接入必须完成：

- 注册、候选解析、固定/随机动画、`--list` 和 `--check`；不把原型主题写成已发布主题。
- 各主题的场景边界、动画终点、待机首尾、深浅背景与字符降级测试。
- Claude / Codex 真终端的开场、输入提交、clear、resize、恢复与窄布局验收。
- 打包后在源码目录外安装验证，确保资源、署名和许可证说明齐全。
- 更新 README 中已可用主题、命令与实拍图。生产回归命令见 `themes.md`。

验收记录按“设计已选定 → 原型通过 → 终端通过 → 发布就绪”标记；
只有最后一项完成才进入首版主题清单。截图记录条件和文件路径，不用截图替代动态验收。

## 已确认的制作方向

以下方向已完成网页原型与来源记录，可在 `prototypes/theme-lab/tech.html` 比较。
六套新增科技主题与 Android 全身改版尚未接入 CLI，也尚未完成真实终端验收。

| ID | 方向与大图 | Claude 小图 | 动作研究方向（不要求全部保留） |
| --- | --- | --- | --- |
| `android` | 保留独立主题，大图改为全身机器人 | 独立头部 | 跳入着陆、回弹挥手 |
| `google` | 独立彩色字标 | G | 四色轨道汇聚、字母落定 |
| `windows` | Windows XP 四色旗，与 Microsoft 拉开年代及轮廓差异 | 蓝色窗格 / 四色方窗 | 旗面展开 |
| `nvidia` | 绿色眼形与字标 | 双风扇显卡 / 原始眼形 | 绿色数字雨构建 |
| `intel` | 经典椭圆环绕字标 | 芯片 | 芯片引脚回收、轨道展开与数据写入；待机双轨道拖尾与字标扫光 |
| `amd` | 字标与几何箭头 | 方形箭头 | 折角核心展开、四路数据汇入；待机数据流与红色脉冲 |
| `microsoft` | 现代四色方块与字标 | 四色方块 | 四向拼合；待机方阵舒展 |

优先推进 Android 的大图差异化与 Google，然后 Windows、NVIDIA、Intel、AMD、Microsoft。
IBM、ThinkPad 保留为后续候选，不计入已承诺的首版数量。
Nintendo、Mario 继续作为两个独立主题；Mario 默认使用人物大图与蘑菇小图。
数量服从验收，不为了凑首版主题数复制同一动画或降低小图质量。

科技原型精修后每套保留一个开场。移除 Google 点阵、Windows 进度条、Intel 电路、
Microsoft 翻片、NVIDIA 碎片、AMD 芯粒和 Android 拆装；原始设计清单仅保留研究记录。
动画验收必须检查中间辅助元素的退出与结束前画面，不能只验证 `frame(3)`。

复查也移除了 PlayStation portal、Nintendo tiles、Xbox sphere 的第二开场；
这些切片方案未能在切回静态之前保持完整一致的轮廓。Mario 两种动作仍保留。

## 统一文字动画（用户确认）

大图下方标题与三行文字统一复用同一套入场、待机动画，只有大图动画随主题变化。
标题入场逐列解码并落定，三行文字依次渐显；待机标题短暂解码，第一与第三行品牌色扫过，第二行稳定。
各主题不得自行修改文字时间轴。网页由 copy-motion.js 共享实现；生产接入复用现有文字渲染与调度，
不将网页 DOM 代码作为终端实现。当前网页为同一机制的设计预览，不声称逐像素复刻终端。

### 中文标题与 Microsoft 色块

任天堂中文标题使用 Noto Sans SC Medium 的矢量轮廓直接拟合终端格，
不再缩放系统字体位图。只在构建时需要字体，运行时仍无字体依赖。
字体来源与 OFL 许可证见 nintendo-SOURCE.txt 和 noto-sans-sc-OFL.txt。
可使用包含「任天堂」的 WOFF2 子集，构建时加 `--with brotli`。

Microsoft 大图在导出前固定为四种品牌纯色，并启用保色采样。
单个终端格无法同时容纳透明背景和两种区域颜色时，舍弃少数交界像素，
不将其染成邻区颜色；开场、静态和待机共用此规则。


### Intel terminal refinement after 0.6.0

取消字母单独增高 16% 的处理，恢复源字标比例。e 的细节通过共享
`pixelOutline` 构建工具做单色网格适配，避免常用终端尺寸下出现单像素毛刺。
入场改为电路汇入芯片、字标压印、经典椭圆闭合；待机光效只在真实笔画内流动，
所有待机帧保持与静态一致的轮廓。下方独立标题继续关闭，小芯片保留方形比例。


### Intel official vector reference

经典字标改为直接提取自 Intel 官方文档 317804-010（2008 年 12 月）封面的
矢量路径。源文档 SHA-256、页码、原坐标和统一归一化矩阵写入 provenance，
`tools/extract_intel_mark.py` 可复现提取并拒绝校验值不符的 PDF。
e 在实际导出管线中校准为 16×19 单色网格；静态、入场和待机使用同一份路径，
不再对字母单独做纵向拉伸。像素适配与主题配色仍是项目设计，未声称获得官方授权。

### 已选顶栏字形

默认使用支持对应字形的 Nerd Font。PlayStation 使用 `md-sony_playstation`
（U+F0414），Xbox 使用用户选择的 `fa-xbox`（U+ED3E），Nintendo 使用
`md-nintendo_switch`（U+F07E1），Mario 使用通用蘑菇 `md-mushroom`
（U+F07DF），Google 使用 `fa-google`（U+F1A0），Microsoft 使用四格标志
`fa-microsoft`（U+ED04）。Huawei、Apple、Android、Intel 保持原字形；
Intel 是通用芯片，NVIDIA 使用通用扩展卡 `md-expansion_card`（U+F08AE），
AMD 使用通用空心右上箭头 `md-arrow_top_right_bold_outline`（U+F09C5），
呼应品牌箭头方向，非官方 AMD Logo。字形名称与码点取自
https://github.com/ryanoasis/nerd-fonts/blob/master/glyphnames.json 。

Nintendo 蓝红小图的左右圆点均适配为独立的 2×2 像素，同时调整左内壁与圆点位置，
使 octant 和 quadrant 下均保持大小一致且不与边框粘连。此改动仅涉及小图，
不改变大图、开场和待机动画。终端视觉验收仍由用户逐套确认。
